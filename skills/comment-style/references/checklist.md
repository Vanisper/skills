# 注释检查清单

在提交或结束修改前过一遍。分两级：**红线**逐条核对，**参考**快速扫读；分语言组按项目实际语言取用。

## 通用红线（任何语言，逐条核对）

1. 注释解释了代码本身看不出的信息（或为长逻辑提供导航），没有复述代码、没有「处理数据」式空话
2. 去留经过「读者收益 vs 维护成本」权衡；自解释性按读者画像（语言背景、领域熟悉度）判断，没拿作者熟悉度代替
3. 没有只给对外 API 写注释而让模块内部裸奔；也没有拿注释补偿本该改名的烂命名
4. 注释与当前实现同步；过时注释、注释掉的死代码已删除（历史交给版本控制）
5. 注释语言与项目主体语言对齐，单文件内一种主注释语言；外部 API 名、协议名、代码术语保留英文
6. API 块注释按域组织（title / description / signature）且域之间空行；标签按四层裁决选择、与项目工具链兼容，未混出两套标签体系
7. 字段、Props、options 的细节下沉到最小作用域（成员本身），没堆在顶层主注释里
8. 首行先写「这是什么」；公共 API 注释只写调用契约（参数、返回值、状态变化、失败条件、顺序规则），未塞架构取舍或「不做什么」

## 通用参考（扫一遍即可）

- title 用标题语法时，层级符合从属关系（顶层符号高于成员）且项目内一致
- 同一组列表的句末标点统一（细则见 [punctuation.md](punctuation.md)）
- 仅当语言有显式 description 标签时，核对该标签按项目既有约定写出（`@description` / `@remarks` 只用一套）
- 默认值已由代码清楚表达时，未额外补默认值标签
- TODO / FIXME 写明了原因和下一步，不留空标记

## 分语言（按项目实际语言看对应组，可插拔）

### TypeScript / JavaScript

- 首导出符号是否单独写了 JSDoc，避免文件级注释被误挂到第一个导出
- 是否用了项目接受的 JSDoc / TSDoc 风格块注释，且未在一个项目里混出两套标签体系
- constructor parameter properties 的说明是否下沉到成员本身，而非堆在主注释

### Rust

- 条目注释是否用了 `///` 而非 `//`，模块级是否用了 `//!`
- 契约是否用 rustdoc 小节组织（`# Examples` / `# Errors` / `# Panics` / `# Safety`）
- doctest 示例是否真的能通过 `cargo test`

### Java / Javadoc

- 分段是否用 `<p>`、列要点是否用 `<ul>`/`<li>`、是否知道空行会被折叠
- `<ul>` 是否闭合；首行是否只写一句概要

### Python

- docstring 是否用 `"""` 且为模块 / 类 / 函数体的第一条语句
- 摘要行与后续描述之间是否空行；风格（Google / NumPy / reST）是否项目内统一不混
- 类型是否交给 type hints，docstring 未重复类型

### Go

- doc 注释是否为整句、以标识符名开头、紧贴声明无空行
- 导出标识符是否都有 doc comment；是否误用了 `@tag`（Go 无标签体系，契约写 prose）
- 示例是否写成 `ExampleXxx` 测试函数而非注释内代码块

### C#

- `<summary>` 是否只写一句，展开内容是否归位 `<remarks>`
- XML 是否良构（标签闭合、特殊字符转义）；泛型 cref 是否用花括号

### C / C++

- 块形态（`/**` vs `/*!` vs `///`）与命令前缀（`@` vs `\`）是否项目内统一
- API 文档是否写在头文件；指针出参是否标注了 `[in]` / `[out]` 方向

### Kotlin

- 弃用是否用 `@Deprecated` 注解而非 KDoc 标签（KDoc 无 `@deprecated`）
- 主构造器属性是否经 `@property` 登记；示例是否优先 `@sample` 引用

### PHP

- docblock 是否与原生类型声明重复（纯重复的删）；泛型集合等超集语法是否与项目所用静态分析器匹配
- `@throws` 是否补齐了会抛出的异常

### Shell

- 文件头是否写清用法、依赖、退出码
- 函数头是否写清各位置参数（`$1` / `$2`）含义、读写的全局变量、输出与返回码

> 新增语言时，在此加一个 `### <语言>` 组，与 [rules.md](rules.md) 路由表的 `lang/<语言>.md` 对应。
