# Shell / Bash

## 现状与定位

- Shell **没有文档注释标准**，只有 `#` 注释与社区惯例（Google Shell Style Guide 是最常被引用的成文惯例；shdoc 等文档工具存在但小众）。
- **惯例覆盖基线**：无标签体系、整句注释可接受，不套用卡片式标点规则。
- shell 无类型系统、参数按位置传递、副作用（全局变量、文件、环境）无从声明——**注释承担的契约职责比其他语言更重**，函数头注释近乎唯一的接口文档。

## 文件头

shebang 下方用盒式头写清用途、用法、依赖与退出码；`set -euo pipefail` 这类改变整个脚本行为的开关值得一句说明：

```bash
#!/usr/bin/env bash
# ============================================================
# 按权重分配数量的批处理入口
# ------------------------------------------------------------
# 用法：distribute.sh <total> <items-file>
# 依赖：jq；读取环境变量 DIST_MODE（可选，默认 even）
# 退出码：0 成功；1 参数错误；2 输入文件缺失
# ============================================================
set -euo pipefail
```

## 函数头

每个非平凡函数写清：用途、各位置参数含义、读写的全局变量、输出（stdout）与返回码：

```bash
# 按权重把总量分配到各项，结果逐行写到 stdout。
# 参数：
#   $1  待分配总量
#   $2  权重列表（空格分隔）
# 全局：读取 DIST_MODE；不修改任何全局变量
# 返回码：0 成功；1 权重列表为空
distribute() {
  # ...
}
```

## 常见坑

- 位置参数不注释 → `$1` `$2` 的含义只能靠通读函数体逆推
- 隐式读写全局变量不登记 → 调用者无从知道副作用
- 非显然的 quoting、子 shell、`IFS` 操作值得行内注释——这些是 shell 特有的读者陷阱
- 脚本超过百行量级时，Google 风格指南的建议是考虑改用更结构化的语言——注释救不了过长的 shell
