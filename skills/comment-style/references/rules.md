# 注释规则

注释的裁判标准是**读者的理解成本**：好注释降低读者读懂代码的成本，坏注释增加维护成本。「注释解释为什么，代码解释怎么做」是有用的倾向，不是禁令——契约、导航、示例同样是好注释的正当形态。

## 权衡模型：何时需要注释

先立轴再判断：**读者收益**（省下多少读代码、踩坑、误用的时间）对 **维护成本**（过时风险、噪音干扰）。两点提醒：

- 自解释性是**相对读者**的属性，不是代码的固有属性。编程语言是英文语境，非英语母语读者对英文标识符天然不敏感；作者不能拿自己此刻对代码的熟悉度代替读者视角
- 不要把「克制」当默认值：模型/工具的默认倾向往往是零注释、或只给对外 API 写注释——这是需要纠偏的失败模式，不是美德

应该补注释的场景：

- 业务规则存在隐含前提、历史包袱或外部依赖
- 有临时方案、技术债、兜底逻辑或兼容性分支
- 算法、正则、位运算、时序控制不直观
- 接口字段、单位、格式、枚举值或返回契约有陷阱
- 示例、调用顺序或副作用不看上下文就容易误用
- 模块 / 包内部的非显然实现——不要只给对外 API 写注释而让内部裸奔；内部读者同样是读者
- 长流程的阶段划分（导航性注释，见「区块注释与折叠」）
- 中文主体项目中，恰当的中文叙述性注释能显著降低读者成本；「英文标识符 + 中文注释」是常见的良性组合

通常不值得写的场景：

- 命名、类型、签名或测试已清楚表达意图，**且按读者画像判断确实自明**
- 直观的条件判断、循环和常规框架用法
- 只会复述代码表面的动作
- 注释掉的旧代码——直接删除，历史交给版本控制，不要拿注释当回收站

## 命名与注释的关系

- 好命名仍是第一位：注释不补偿烂命名，能靠改名解决的先改名
- 但「顾名思义」不是一刀切的准则：非母语团队、领域术语、生僻缩写都会让「自解释」失效——名字对作者顾名思义，对读者未必
- 判断时用读者画像：这个项目的维护者是谁、语言背景如何、对领域多熟悉，而不是作者自己的熟悉度

## 注释的构成（域模型）

API 注释是结构化卡片，不是文章。按内容职责分为三个基本域，按需再加扩展域，**域之间空一行**：

- **title 域**：首行，一句话定位「这是什么」。可用 markdown 标题语法强化结构，层级随符号的从属关系——顶层符号（类、接口、导出函数）可用一级标题，成员（方法、属性）用二级或三级；具体用几级是观感取舍，项目内保持一致即可。标题自成段落，下一行可直接续写辅助描述而不粘连；不用标题语法时，主副标题之间必须空一行，否则渲染时会被空格连成一行
- **description 域**：契约要点的展开。有显式 description 标签的语言，标签名跟随项目既有约定（`@description` 或 `@remarks`），不要按本 skill 示例另起一套；无此类标签的语言用空行后的段落承接。可同行直接描述，也可空行后分点列表
- **signature 域**：签名事实的归纳——入参、出参、抛错、默认值等工具可解析的契约
- **example / see 域**（按需扩展）：`@example` 使用示例、`@see` / `@link` 关联引用。「使用向」注释（组件、对外库）可用更丰富的 markdown——链接、`***` 分隔线等，hover 按 markdown 渲染

空行规则由渲染折叠推出来：文档注释最终渲染为 markdown 或 HTML，相邻行都会被折成一段（以空格连接）。「空行是否分段」因渲染目标而异——markdown（JSDoc hover、rustdoc、KDoc）里空行才分段，因此「标题自成一行」「无语法标记的主副标题必须空行」「域之间空行」是同一件事的三种表现；经典 Javadoc 等 HTML 文档里空行也被折叠，分段必须用 `<p>` 等块级标签（JDK 23+ 的 markdown 文档注释除外）。各语言的具体差异见对应 lang 文件。

完整形态示例（顶层符号，标题域用一级标题）：

```ts
/**
 * # 按权重分配数量到目标项
 *
 * - 权重为 0 的项自动跳过
 * - 末项承担余量，保证总量守恒
 *
 * @param total 待分配总量
 * @param items 目标项数组
 * @returns 顺序与输入一致的分配结果
 *
 * @example
 * ```ts
 * distribute(100, [
 *   { id: 'A', weight: 3 },
 *   { id: 'B', weight: 7 },
 * ])
 * ```
 */
```

标题语法是可选强化：不用标题时 title 就是普通首行，其余域规则不变。类成员用二级/三级标题的变体见 [lang/typescript.md](lang/typescript.md)。

## 语境区分

源码注释与文档正文是两种语境，标点规则不同：

- **源码注释**：力求精炼，只写契约、约束、边界、原因，不复述代码；中文注释一般不以句号结尾——句号是「成篇文章」的标点，而 API 注释是结构化卡片（见「注释的构成」）：title 是定位短语、分点是精练碎片、signature 是契约事实，都不是句子；完整句子只通行于实现内的流程注释；成文整句惯例（Go / Python）优先，见「强语言惯例优先」
- **Markdown 文档正文**：是正常文章语境，按文章结构使用标点，不受上述注释标点规则约束

英文注释以项目现有风格为准，不必为了去标点而牺牲可读性（skill 补充惯例，非通用铁律）。

豁免：`@deprecated` 迁移说明、安全警告这类需要讲清「为什么 + 怎么办」的内容，可用完整句子。

## 强语言惯例优先

基线的「标签体系 + 首行定位短语 + 中文不以句号结尾」卡片模型源自 JSDoc / TSDoc 语境。当某门语言存在**成文的强约定**时，语言惯例优先于基线的标点、首行与标签规则：

- **Go（godoc）**：doc 注释是整句、以标识符名开头、句号结尾，且没有标签体系
- **Python（PEP 257）**：docstring 摘要行是句末带句号的整句
- **Shell**：无文档注释标准，整句 `#` 注释即惯例

差异一律在对应 lang 文件显式登记，本文件不展开。上一节「英文注释以项目现有风格为准」正是这条原则的特例。

## 列表标点

列表项的句末标点按语法结构判断：

- 短语、词组、简短分句不加句末标点
- 完整句，或含逗号、分号的复杂项，可加句号
- 同一组列表保持一致，不要一半加句号一半不加

## 语言与语气

- 注释语言与项目主体语言对齐；外部 API 名、协议名、代码术语保留英文。
- 单个文件内尽量只保留一种主注释语言。
- 第一行优先写“这是什么”，不要先写过程描述。
- 长句拆成列表，让约束、顺序和边界一眼可扫。能写成一句长话的说明，优先提炼为「冒号 + 分点」两段式——冒号前是要点的总结，分点罗列关键内容，结构先于句子出现。

## 注释层级

### 文件头与局域头注释

当一个文件承载明确职责、阶段划分或隐藏约束时，可以使用多行 `//` 盒式注释做文件头，避免 `/** */` 被错误关联到下方第一个导出。

```ts
// ============================================================
// 订单商品项归一化拆分器
// ------------------------------------------------------------
// - 按优先级重新分配数量
// - 同优先级保持原订单顺序
// - 末项承担余量，保证总量守恒
// ============================================================
```

同样的盒式注释可用于**局域头**：文件内某个自成一体的区域需要整体叙述时（如 Vue SFC 的 `<script>` 顶部对组件职责的总述、一段平台分支的开场说明），形态不变、作用域缩小。Vue 组件的「对使用者的描述」与 IDE hover 的关系见 [lang/typescript.md](lang/typescript.md) 的 Vue / React 节。

### API 块注释

对下面这些对象优先使用 JSDoc / TSDoc 风格块注释：

- 导出函数、类、接口、类型
- 公共组件、公共 Hook、复用工具函数
- 即使不导出，但契约、边界或副作用明显不直观的内部符号

不要把“所有跨文件消费”都机械地升级成块注释；也不要反过来只给导出符号写注释、让内部实现完全裸奔——两个方向都用「权衡模型」裁决。

- API 注释面向使用者写调用契约：参数、返回值、状态变化、失败条件、顺序规则。
- 架构取舍、模块边界、“不做什么”这类背景写进项目文档，不要塞进 API 注释。
- 块注释内部按域组织（title / description / signature），构成与空行规则见「注释的构成（域模型）」。

```ts
/**
 * 按权重分配数量到目标项
 *
 * @description
 * - 权重为 0 的项自动跳过
 * - 末项承担余量，保证总量守恒
 *
 * @param total 待分配总量
 * @param items 目标项数组
 * @returns 顺序与输入一致的分配结果
 */
```

### 区块注释与折叠

区块注释是长逻辑的**导航**：为阶段划分立标题，帮读者建立地图——这是实现内部的正当注释，不是噪音；但不要给每一两行代码都加标题。

```ts
// 校验输入完整性
// 按优先级排序
// 计算剩余未分配数量
```

需要 IDE 折叠时再用 `//#region` / `//#endregion`，常见于生命周期、平台分支或多个并列逻辑单元。

### 行内注释

行内注释只解释局部陷阱、取舍或“为什么不这么写”。

```ts
// 故意不用 await，避免串行发送导致蓝牙缓冲区阻塞
queueWrite(packet)
```

## 类型、字段与 Props

- 把注释理解为主从两层：主注释说明整体对象是什么、承担什么职责；从注释说明具体字段、属性或成员的含义与约束。
- 接口或类型的首行先写“这是什么数据结构”。
- 类、接口、type 的主注释只说明整体职责、整体契约或整体约束，不替成员字段逐个下注释。
- 字段级细节尽量下沉到字段本身，不要把所有字段说明都堆在接口主注释里。
- 只给存在陷阱、格式约束、单位差异或枚举语义的字段补注释。
- Props、options、配置对象优先说明格式、单位、默认行为和 callback 触发时机。
- 这条规则对 interface 字段、class 属性、对象字面量字段和 TypeScript 的 constructor parameter properties 一样成立；字段含义写在对应成员上，不要塞进主注释的 `@remarks` 或 `@description`。

```ts
/**
 * 供应商原始响应结构
 *
 * @description 后端字段为 snake_case，进入业务层前需先归一化
 */
interface RawSupplierResponse {
  /** 供应商名称 */
  s_name: string

  /**
   * 启用状态
   * - '0' 禁用
   * - '1' 启用
   */
  is_active: '0' | '1'
}
```

```ts
/**
 * 打点单归一化结果
 *
 * @description 保存归一化后的票据、目标项和计算结果
 */
export class SpotTicketNormalization {
  constructor(
    readonly ticket: SpotTicket,
    readonly targetItems: readonly OrderItem[],
    /** 目标总量 */
    readonly baseQty: Quantity,
    /** 用户录入总量 */
    readonly inputTotalQty: Quantity,
    readonly outcomes: readonly NormalizedOutcome[],
  ) {}
}
```

## 标签与分语言惯例

标签「该用什么、不该用什么」按**四层裁决顺序**归位，事实与口味不混写：

1. **规范依据**——标准原文怎么说（JSDoc、TSDoc、Javadoc、rustdoc、godoc 等均有成文规范；各 lang 文件尾部「规范依据」小节给出处与查证日期）
2. **工具链现实**——项目所用工具的实测行为（如经典 jsdoc CLI 对 `@description` 的处理、IDE hover 的渲染差异）
3. **项目现状**——既有约定优先，不在一个项目里混出两套体系
4. **个人口味**——显式标注为口味，他人可按项目情况取舍

通用、稳定的标签（`@param`、`@returns`、`@example`、`@throws`、`@see`、`@deprecated`）跨语言通用；标签选择、文档注释符号、doc 工具链的具体惯例按语言拆分，按项目实际语言查对应文件：

- TypeScript / JavaScript / JSDoc（标签四层裁决、域布局、Vue / React 差异）→ [lang/typescript.md](lang/typescript.md)
- Rust（`///`、`//!`、rustdoc 小节）→ [lang/rust.md](lang/rust.md)
- Java / Javadoc（`<p>`、`<ul>` / `<li>`、空行折叠）→ [lang/java.md](lang/java.md)
- Python（docstring、PEP 257、三种风格）→ [lang/python.md](lang/python.md)
- Go（godoc 整句惯例、无标签体系）→ [lang/go.md](lang/go.md)
- C#（XML 文档注释）→ [lang/csharp.md](lang/csharp.md)
- C / C++（Doxygen）→ [lang/cpp.md](lang/cpp.md)
- Kotlin（KDoc、Dokka）→ [lang/kotlin.md](lang/kotlin.md)
- PHP（PHPDoc、phpDocumentor 事实标准）→ [lang/php.md](lang/php.md)
- Shell（无标准下的头注释惯例）→ [lang/shell.md](lang/shell.md)
- 新增语言：加一个 `lang/<语言>.md`，并在此列表与 [SKILL.md](../SKILL.md) 路由表、[checklist.md](checklist.md) 分语言组登记，不改动本文件其余内容。

## TODO / FIXME

- `TODO` 用于计划中的改进
- `FIXME` 用于已知错误、缺陷或不正确行为
- 不要只留空标记，至少补充原因和预期处理方向；如果已知负责人、条件或时间窗口，也可以一并写明

```ts
// TODO: 等后端统一返回 UTC 时间后移除本地时区兜底
// FIXME: 当前正则无法匹配嵌套括号，需改为状态机解析
```

## 质量标准

好的注释通常满足：

- 解释了代码本身看不出来的信息，或为长逻辑提供导航
- 作用域足够小，贴近真实约束出现的位置
- 和当前实现保持同步，重构后依然成立
- 例子只在确实能降低误用风险时出现

坏的注释通常表现为：

- 只是把代码翻译成自然语言
- 用“处理数据”“设置状态”这类空话
- 已经过时，和当前返回值、时序或实现不一致
- 为所有变量和每一行循环都加说明
- 注释掉的旧代码当仓库用——历史该交给版本控制
