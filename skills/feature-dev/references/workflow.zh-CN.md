# 功能开发工作流

这份参考把 Anthropic Claude Code 的 `feature-dev` 插件改写成 Codex 可用的 skill 流程。任务足够复杂、主 `SKILL.md` 的清单不够细时再读取。

## 阶段 1：发现需求

目标：弄清要做什么，以及为什么做。

- 用具体语言复述用户需求。
- 识别要解决的问题、期望行为、约束和成功标准。
- 判断已有信息是否足够开始探索代码。
- 只有当缺失信息会改变搜索方向或无法界定范围时，才立即提问。

输出：

- 简短的理解总结。
- 如果工作量较大，给出小型任务计划。

## 阶段 2：探索代码库

目标：设计前先理解现有实现模式。

从多个角度探索：

- 相似功能及其实现路径。
- 入口点，例如路由、命令、组件、handler、job、API。
- 架构边界，例如 UI、领域逻辑、持久化、service、adapter、测试和配置。
- 项目约定，例如文档、现有代码、测试、lint 配置，以及 `AGENTS.md`、`CLAUDE.md` 等 agent 指令文件。
- 相关测试模式和 fixture。

优先使用：

- 编辑前执行 `git status --short --branch`。
- 用 `rg --files` 发现文件。
- 用 `rg` 搜索符号和现有术语。
- 搜索后阅读关键文件，不只依赖片段。

输出：

- 发现的关键模式和文件引用。
- 需要阅读或修改的重要文件。
- 可能的集成点和风险。

## 阶段 3：澄清问题

目标：在设计和实现前消除关键歧义。

可以询问：

- 用户可见行为、非目标。
- 边界情况、错误处理、加载态、空状态、权限和兼容性。
- 数据模型、迁移、持久化、外部服务、安全和性能需求。
- API 契约、灰度、向后兼容和测试预期。

判断方式：

- 当歧义影响架构、用户体验、数据、公共契约、安全或不可逆操作时，等待用户回答。
- 对低风险细节，说明合理假设并继续。
- 如果用户说“你看着办”，先给出建议；风险可控时继续，风险较高时等用户确认。

## 阶段 4：架构设计

目标：选择适合代码库的方案。

较大的功能可以比较 2-3 个方案：

- 最小改动：最小 diff，最大复用。
- 清晰架构：边界更好，更易测试和维护。
- 务实平衡：保持足够结构，同时避免大范围重构。

每个可行方案说明：

- 要创建或修改的文件。
- 组件职责。
- 数据流和状态归属。
- 集成点和公共契约。
- 测试计划。
- 取舍和风险。

最后给出推荐。如果选择会明显影响产品行为、数据形态、公共 API 或长期架构，先让用户选择再实现。

## 阶段 5：实现

目标：按选定方案构建功能。

- 改动聚焦在当前功能。
- 遵循已发现的项目约定和本地 helper API。
- 在行为附近更新或补充测试。
- 优先使用小而清楚的抽象，避免大范围重写。
- 保留工作区里与任务无关的用户改动。
- 手动编辑使用 `apply_patch`。
- 重大编辑前、长命令运行中，给用户简短进度更新。

## 阶段 6：质量审查

目标：在最终回复前抓住真正重要的问题。

审查：

- 正确性和边界情况。
- 错误处理、异步或状态竞争。
- 安全和权限边界。
- 数据迁移或兼容性风险。
- 重复、抽象不清、偏离项目约定。
- 变更行为缺少测试。
- 涉及前端时检查布局和可访问性。

验证优先从最小有用命令开始，风险高时再扩大范围：

- 针对改动代码的单元测试。
- 可用时运行 typecheck 或 lint。
- 跨模块改动运行 build 或定向集成测试。
- 重要前端改动做浏览器或视觉验证。

如果发现问题，能修就修；不能修则清楚说明残余风险。

## 阶段 7：总结

目标：让结果容易理解。

最终回复包含：

- 改了什么。
- 重要决策或假设。
- 做了哪些验证。
- 有价值的剩余风险或后续事项。
