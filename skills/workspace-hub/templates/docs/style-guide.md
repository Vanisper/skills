# 书写与注释规范

总原则：书写语言与项目主体语言风格对齐。本篇以中文语境给出细则示例；本工作空间主体语言为 {{primary_language}}，若与中文不同，须按总原则改写细则的对应语言版本（标点、注释惯例等）。本规范适用于本工作空间的全部文档，并作为体系内各项目仓库的默认规范；项目可按自身情况覆写，覆写内容写进该项目自己的约定文件。

本篇只定**工作空间级偏好**（语言、标点、列表）。注释去留与组织按**读者理解成本**权衡，不另起一套注释规范；若项目使用 `comment-style` skill，以其为准。

## 语境区分

编程语言、API、类型系统与工具链基本以英文为主，中文插入代码环境时的视觉重量与阅读节奏都与纯文章不同。两种语境适用不同规则，不要把注释规则机械套用到文档正文：

- 源码注释：力求精炼，只说明契约、约束、边界与原因，不用中文复述代码。
- Markdown 文档正文（README、设计文档等）：正常文章语境，按文章自身的结构与表达目的使用标点。

## 标点

- 中文行文用全角标点；英文工具名、代码引用保持原文。
- 列表项标点按语法结构决定：短语、词组、简短分句不加句末标点；完整句子或内部已含逗号/分号的复杂项可用句号收尾。
- 同一组列表保持统一，不要「有的加句号、有的不加」混用。
- 源码注释的摘要行一般不以句号结尾（精炼语境的惯例）；文档正文不受此限。

## 源码注释原则

- 注释语言与项目主体语言对齐：本体系以{{primary_language}}为主体语言，源码注释用{{primary_language}}；外部 API 名、协议名、代码术语保留英文。
- 注释去留按读者理解成本权衡：读者收益对维护成本。不要把「零注释 / 只给对外 API 写注释」当默认美德，也不要用注释复述代码或补偿烂命名。
- 公开 API 写调用契约；模块内部的非显然实现、阶段划分、隐含约束同样值得注释。
- 架构取舍、模块边界、「不做什么」这类内容写进项目文档，不塞进使用者会直接读到的 API 注释。

## 分语言惯例

<!-- 以下小节按体系实际技术栈增删；此处保留 Rust 与 TypeScript 两例 -->

其他语言引入时按该语言文档工具的渲染规则补充对应惯例（例如 Javadoc 会折叠空行，分段需显式 HTML 标签）。标签名、域怎么组织，跟随项目既有约定或 `comment-style`，本篇不另定。

### Rust

- 条目注释用 `///`，模块 / crate 级说明用 `//!`。
- 首行为一句话摘要，展开说明另起段落；小节遵循 rustdoc 通用惯例（Examples、Errors、Panics、Safety 等）。

### TypeScript / JavaScript（JSDoc）

- 摘要与补充说明之间保留一个空行，保证渲染时换行。补充说明用什么标签跟随项目既有约定，本篇不指定唯一写法。
- 多个要点用列表，标点遵循上文列表规则；契约标签视情况使用。
- 文件顶部若有文件级注释，须为第一个导出符号单独写 JSDoc，避免文档工具把文件级注释误挂到该符号上。

示例：

```ts
/**
 * 根据传入的 id 列表调整顺序
 *
 * - 只调整已注册 item 的顺序
 * - 未传入的已注册 item 保留在末尾
 */
setOrder(ids: readonly ItemId[]): void
```
